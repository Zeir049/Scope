# Glitch 백엔드 — 발표 자료 정리

> 이 문서는 발표(슬라이드) 제작용 원고입니다. 각 `##` 섹션이 대략 슬라이드 한 장에 대응합니다.

---

## 0. 한 줄 요약

> **이야기의 설정 모순을 잡아주는 AI 서비스 'Glitch'의 백엔드를 만들었고,
> AI만 나중에 끼우면 되도록 설계했으며, 전체 흐름이 실제로 작동하는 것까지 검증했다.**

---

## 1. 배경 & 문제

- 웹소설처럼 **긴 이야기**를 쓰면 앞뒤 설정이 어긋나는 실수가 쌓인다.
  - 예: 인물의 나이·성격이 도중에 바뀜, 세계관 규칙이 서로 모순됨, 복선이 회수되지 않음.
- 사람이 수백 회차를 일일이 대조하기는 어렵다 → **AI가 자동으로 모순을 잡아주자.**

---

## 2. 목적 & 범위

**만드는 것:** Glitch 서비스의 **백엔드 '몸통(게이트웨이)'**

- 담당: 회원 인증 · 작품/회차 관리 · 원고 저장 · **분석기 호출** · 결과 저장(설정 누적)
- **범위 밖(의도적 분리):** 실제로 모순을 찾아내는 **AI 두뇌**는 별도 영역.

**핵심 설계 목표**

> "바뀔 것(AI 분석기, 메일, 파일 저장 등)은 전부 **교체 가능한 부품**으로 숨겨,
> 나중에 무엇을 갈아끼워도 핵심 로직은 안 건드리게 한다."

---

## 3. 무엇을 했나 (진행 요약)

1. **규칙 정의 후 백엔드 구축** — 코드가 지켜야 할 원칙을 정하고 그대로 구현.
2. **디자인 시안(피그마) ↔ 기능 대조** — 빠진 기능 6가지를 찾아 보완.
   - 프로젝트 편집·썸네일, docx 업로드, 작업 채팅, 구독, 공유 링크·알림, 비밀번호 재설정.
3. **데이터 안전장치 보강** — 설정 이력이 꼬이지 않도록 DB 제약 추가.
4. **전체 작동 검증** — 일회용 스모크 테스트로 로그인→분석→저장 한 바퀴를 실제로 돌려 확인.

## 5. 아키텍처 (1) — 레이어 분리

**의존 방향은 위 → 아래 한 방향으로만.** 섞이면 유지보수가 불가능해지므로 층을 나눔.

```
api/         HTTP 입출력·검증만        (문지기)
  └ service/     비즈니스 로직·트랜잭션   (머리)
      └ repository/  DB 접근(SQL은 여기만)  (손)
          └ models/      테이블 정의        (뼈대)
```

- 라우터는 service만 호출, service는 repository만 통해 DB 접근.
- 요청/응답 모양(schemas)과 DB 모양(models)을 분리해 내부 노출 방지.

---

## 6. 아키텍처 (2) — '계약'으로 분석기 분리 (핵심)

바뀔 부분을 **인터페이스(계약) 뒤로 숨긴 것**이 이 설계의 핵심.

- **계약** (`pipeline/interface.py`): `analyze_chapter(글, 기존설정) → 분석결과` 한 줄 약속.
- **구현체**: `fake`(가짜) · `remote`(외부 AI 서버) · `local`(같은 프로세스) — 계약을 각자 방식으로 이행.
- **선택 장치** (`factory.py`): 설정값 `PIPELINE_MODE`로 셋 중 하나를 주입.
- 몸통은 "파이프라인"이라는 추상만 알 뿐, 안이 가짜인지 진짜인지 **모른다.**

> 결과: 진짜 AI가 준비되면 **코드 수정 없이 설정 한 줄**(`fake` → `remote`)로 교체.

같은 방식으로 **메일 발송 · 파일 저장 · 작업 채팅**도 전부 교체 가능한 부품으로 구성.

---

## 7. 가상 LLM은 어떻게 생겼나

지금은 진짜 AI 대신 **평범한 코드(대역)**가 계약을 이행한다. 학습 모델·외부 호출 없음.

- **스모크용** (`smoke/llm.py`): 글을 받으면 무조건 `"ok"` 반환 — 경로가 뚫렸는지만 확인.
- **분석 파이프라인용** (`pipeline/fake.py`): 1초 지연(분석하는 척) 후 **정해둔 모순·설정 데이터**를 반환.
- 둘 다 **진짜가 지킬 계약과 똑같은 입출력**을 가져서, 나중에 그대로 갈아끼울 수 있다.

---

## 8. 실행 흐름 — 회차 분석 한 번의 여정

`chapters.status` 가 `uploaded → analyzing → reviewed → saved` 로 흐르는 것이 뼈대.

1. **접수** — `POST /chapters/{n}/analyze` 요청.
2. **상태만 바꾸고 즉시 응답** — 상태를 `analyzing`으로 커밋 후 `202` 반환(대기하지 않음).
3. **뒤에서 분석 시작** — 백그라운드 작업이 자체 DB 세션을 열어 실행(요청과 분리).
4. **입력 조립** — 현재 설정(`is_current=true`)을 모아 `CanonSnapshot` 생성.
5. **계약 호출** — `analyze_chapter(원고, 스냅샷)` → (가짜는 1초 후) 결과 반환.
6. **저장 + 상태 전환** — 결과를 저장하고 상태를 `reviewed`로. (에러 시 `failed`)
7. **폴링** — 화면은 `GET /result`를 반복 호출해 `reviewed`가 되면 결과 표시.
8. **저장(설정 누적)** — [저장하기] 시 변경분을 **덮어쓰지 않고 새 버전으로 누적**하고 `saved`로 (한 트랜잭션).

---

## 9. 작동 검증 — 스모크 테스트 (성과)

**전체 스택이 실제로 도는지** 확인하는 일회용 테스트를 만들어 돌림.

- 흐름: 웹 화면 로그인 → 프로젝트 생성 → 글 입력 → 가짜 LLM이 `"ok"` 반환 → **DB 저장**.
- 결과: `smoke_checks` 테이블에 `response = ok` 기록 확인 (SQL로 눈으로 검증).
- 의미: **"설계만 그럴듯한 게 아니라 끝까지 실제로 작동한다"를 증명.**
- 성격: 일회용 격리 모듈 → 진짜 AI가 붙으면 폴더 삭제로 깔끔히 제거.

## 11. 앞으로 할 일 (로드맵)

1. **구글 로그인 연동** — 지금은 이메일/비밀번호만.
2. **외부 공개** — 우선 임시 터널로 남에게 테스트 → 이후 무료 클라우드 배포.
3. **'대역' → 실제 구현 교체** — 진짜 모순 검출 AI, 실제 메일 발송, 클라우드 파일 저장.
   - 설계상 각각 **부품 하나 + 설정 한 줄**로 교체 가능.

## 12. 결론

> **"이야기의 설정 모순을 잡는 AI 서비스의 백엔드를,
> AI만 나중에 끼우면 되도록 완성했고, 전체 흐름이 실제로 작동하는 것까지 검증했다."**

- 잘 나눈 구조 + 교체 가능한 설계 → **미래 변경에 강하다.**
- 가짜 대역으로 먼저 완성·검증 → **AI 없이도 제품 전체를 만들고 테스트했다.**
